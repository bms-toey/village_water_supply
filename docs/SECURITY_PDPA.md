# ความปลอดภัยและการคุ้มครองข้อมูลส่วนบุคคล — AquaFlow Pro

เอกสารนี้สำหรับคณะกรรมการ ผู้ดูแลระบบ และนักพัฒนา สรุปสิ่งที่ระบบบังคับไว้แล้ว (ตั้งแต่ `sql/sql_phase5_security.sql`)
และสิ่งที่หน่วยงานต้องทำเองตาม พ.ร.บ.คุ้มครองข้อมูลส่วนบุคคล พ.ศ. 2562 (PDPA) และ ISO/IEC 27001:2022

> สิ่งที่ "ระบบบังคับ" หมายถึงบังคับที่ฐานข้อมูล (trigger / RLS / RPC) — แม้มีคนยิง API ตรงโดยไม่ผ่านหน้าแอป ก็ทำไม่ได้

กฎที่ใช้กับทุกตำแหน่ง (รวม super_admin):

- บิลที่ **ชำระแล้ว** แก้ไม่ได้ / สถานะ "ชำระแล้ว" มาจากใบเสร็จเท่านั้น (ตั้งเองไม่ได้) / ยกเลิกใบเสร็จ → server คืนสถานะบิลให้เอง
- ใบเสร็จที่ออกแล้ว แก้ยอด ช่องทาง วันที่ บิล ไม่ได้ — ยกเลิกแล้วออกใหม่เท่านั้น / ยกเลิกใบเสร็จเงินสดในวันที่ปิดยอดแล้วไม่ได้
- ยอดชำระต้องเท่ากับยอดบิล / บิลหนึ่งใบมีใบเสร็จที่อนุมัติได้ใบเดียว
- งวดที่ปิดแล้ว: แก้ยอด ค่าปรับ สถานะ ไม่ได้ (ยกเว้นงานค่าปรับรายวันและการรับชำระ) — ปรับยอดผ่าน CN/DN
- จดมิเตอร์ได้ครั้งเดียวต่อสมาชิกต่องวด / เลขครั้งก่อนต้องตรงกับในระบบ (กันแก้เลขเดิมเพื่อลดหน่วย)
- ผู้ทำรายการ (ผู้จด ผู้ออกบิล ผู้รับเงิน ผู้อนุมัติ ผู้ยกเลิก ผู้ลบ) server บันทึกจาก token — ปลอมไม่ได้

## 2. ข้อมูลส่วนบุคคลที่ระบบเก็บ

| ข้อมูล | เก็บที่ | การป้องกัน |
|---|---|---|
| ชื่อ-นามสกุล บ้านเลขที่ หมู่บ้าน | `members` | เฉพาะเจ้าหน้าที่ (RLS), TLS |
| เลขบัตรประชาชน | `app_private.member_pii` (เข้ารหัส pgcrypto, กุญแจ `app_pii_key` ใน Vault) + `members.national_id_last4` | client อ่านค่าที่เข้ารหัสไม่ได้เลย, แอปเห็น 4 ตัวท้าย, ดูเต็มได้เฉพาะ admin ผ่าน `reveal_national_id` (บันทึก audit), ไม่อยู่ใน audit log |
| เบอร์โทร อีเมล LINE ID | `members` | เฉพาะเจ้าหน้าที่, ปิดบังในรายการ (081-xxx-5678) |
| พิกัดบ้าน (GPS) | `members.gps_lat/lng` | เฉพาะเจ้าหน้าที่ |
| LINE user ID ที่ผูกไว้ | `member_access.line_user_id` | อ่านผ่าน RPC เท่านั้น, หลุดเมื่อสร้างรหัส portal ใหม่ |
| รหัส portal | `member_access.portal_code` | อ่านได้เฉพาะ finance/admin, ไม่ส่งทาง LINE, ไม่อยู่ในไฟล์สำรอง / audit |
| รูปมิเตอร์ รูปแจ้งซ่อม สลิปโอนเงิน | Storage bucket ส่วนตัว (`meter-photos`, `member-uploads`, `payment-slips`) | เจ้าหน้าที่ / เจ้าของ (สมาชิกเห็นแค่ของตัวเอง), แก้/ลบไม่ได้ |
| ประวัติการใช้น้ำ บิล การชำระ ยอดค้าง | `meter_readings`, `bills`, `payments` | เฉพาะเจ้าหน้าที่, สมาชิกเห็นของตัวเองใน portal |
| บัญชีเจ้าหน้าที่ | `profiles` | อ่านผ่าน RPC เท่านั้น, รหัสผ่าน bcrypt cost 12 |
| ประวัติการแก้ไข | `audit_logs` | แก้/ลบไม่ได้ (trigger), hash chain, ตัด secret และเลขบัตรออก |
| ข้อมูลในเครื่องเจ้าหน้าที่ | localStorage / IndexedDB (คิวจดออฟไลน์) | ล้างเมื่อออกจากระบบ / session หมดอายุ |

ผู้ประมวลผลข้อมูลภายนอก: Supabase (ฐานข้อมูล/ไฟล์), LINE (LY Corporation — ส่งข้อความ), ThaiBulkSMS (SMS),
OpenRouter และผู้ให้บริการโมเดล AI (อ่านรูปมิเตอร์ — **ส่งรูปออกนอกประเทศ**)

## 5. ขั้นตอนรับคำขอใช้สิทธิ์ของเจ้าของข้อมูล (มาตรา 30–36)

1. ผู้ใช้น้ำยื่นคำขอใน portal (เมนู "ข้อมูลของฉัน") — เลือกประเภท: ขอดู/ขอสำเนา, ขอโอนข้อมูล, ขอแก้ไข, ขอลบ, คัดค้าน, ขอระงับ, ถอนความยินยอม
   (ยื่นทางกระดาษก็ได้ — เจ้าหน้าที่บันทึกแทนไม่ได้ในระบบ ให้เก็บเอกสารไว้)
2. ระบบแจ้งเตือน super_admin / village_admin ทันที — **ต้องตอบภายใน 30 วัน** (คอลัมน์ `due_at`)
3. ผู้ดูแลเปิด ตั้งค่า → คำขอ PDPA → ตรวจตัวตน → ดำเนินการ:
   - ขอดู/ขอสำเนา/โอนข้อมูล: ผู้ใช้น้ำดาวน์โหลด JSON ได้เองในหน้า "ข้อมูลของฉัน"
   - ขอแก้ไข: แก้ในหน้าสมาชิก
   - ขอลบ: ปิดสมาชิก → ถ้าไม่มีหนี้ค้าง กด "ทำข้อมูลนิรนาม" (บิล/ใบเสร็จยังเก็บตามกฎหมายบัญชี แต่ไม่ระบุตัวตน)
     ถ้ายังมีหนี้หรืออยู่ในระยะเก็บเอกสาร → ปฏิเสธพร้อมเหตุผล (ม.33 วรรคหนึ่ง)
   - ถอนความยินยอม LINE: ผู้ใช้น้ำพิมพ์ "ยกเลิกการผูก" ในแชท หรือเจ้าหน้าที่สร้างรหัส portal ใหม่
4. ปิดคำขอเป็น "เสร็จ" หรือ "ปฏิเสธ" พร้อมคำตอบ (บังคับ) — ผู้ใช้น้ำเห็นคำตอบใน portal ทุกขั้นตอนบันทึก audit

## 6. เมื่อข้อมูลรั่วไหล / ถูกเจาะระบบ

**แจ้ง สคส. ภายใน 72 ชั่วโมง** นับจากรู้เหตุ (ยกเว้นไม่มีความเสี่ยงต่อสิทธิของบุคคล) และ **แจ้งเจ้าของข้อมูลโดยไม่ชักช้า** ถ้ามีความเสี่ยงสูง (ม.37(4))

1. **ควบคุมเหตุ** — ปิดบัญชีที่ต้องสงสัย (จัดการผู้ใช้ → ปิดใช้งาน), ถ้ารุนแรง ปิดเว็บชั่วคราว
2. **เพิกถอน session ทั้งหมด** — SQL Editor: `UPDATE profiles SET token_version = token_version + 1;` (ทุกคนต้อง login ใหม่)
   สมาชิก portal: สร้างรหัส portal ใหม่ให้รายที่เกี่ยวข้อง
3. **เปลี่ยนกุญแจ**
   - JWT secret ของโปรเจกต์ (Supabase → JWT Keys) แล้วอัปเดต Vault `app_jwt_secret` — ทุก token เดิมใช้ไม่ได้
   - `OPENROUTER_API_KEY`, `LINE_CHANNEL_ACCESS_TOKEN` / `LINE_CHANNEL_SECRET`, `DISPATCH_SECRET`, key SMS
   - **`app_pii_key` ห้ามเปลี่ยนทันที** — ต้องถอดรหัสด้วย key เดิมแล้วเข้ารหัสใหม่ก่อน (ไม่งั้นเลขบัตรอ่านไม่ได้)
4. **ตรวจหลักฐาน** — เรียก `verify_audit_chain()` (admin) ว่า audit ถูกแก้หรือไม่, ดู audit log ช่วงเวลาที่เกิดเหตุ, Supabase logs
5. **ประเมินความเสี่ยงและแจ้ง** — ข้อมูลอะไร กี่ราย → แจ้ง สคส. (แบบฟอร์มที่ pdpc.or.th) และเจ้าของข้อมูล
6. **บันทึกเหตุการณ์** — เวลา สาเหตุ ผลกระทบ การแก้ไข (เก็บเป็นเอกสารแม้ไม่ต้องแจ้ง)

## 9. สิ่งที่หน่วยงานต้องทำเอง (ระบบช่วยไม่ได้)

- แต่งตั้ง DPO — **บังคับถ้าผู้ดำเนินการเป็น อปท.** (หน่วยงานรัฐ) ไม่งั้นกำหนดผู้ติดต่อเรื่องข้อมูลส่วนบุคคล
- ทำสัญญาประมวลผลข้อมูล (DPA) กับ Supabase, LINE (LY Corp), ThaiBulkSMS, OpenRouter
- ยืนยันภูมิภาคของโปรเจกต์ Supabase (แนะนำ Singapore) และระบุในประกาศความเป็นส่วนตัว / ROPA
- ตัดสินใจว่าจำเป็นต้องเก็บเลขบัตรประชาชนหรือไม่ — ถ้าไม่จำเป็น ไม่ต้องกรอก (หลักเก็บเท่าที่จำเป็น ม.22)
- อบรมเจ้าหน้าที่, ทบทวนสิทธิ์ผู้ใช้ทุกไตรมาส, ปิดบัญชีคนที่ลาออกทันที
- ยังไม่ได้ทำในระบบ: MFA สำหรับ admin/finance, จำกัดเจ้าหน้าที่ให้เห็นเฉพาะหมู่บ้านตัวเอง, ลบรูป/สลิปเก่าอัตโนมัติ, ล็อกหน้าจออัตโนมัติ
